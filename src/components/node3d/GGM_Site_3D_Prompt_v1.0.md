# GGM — 3D-сцена «Объект → здание → помещение → шкаф»: промпт v1.0 (27.10.2026)

Назначение: полный промпт для реализации интерактивной 3D-сцены сайта Green Grid Mind. Сцена объясняет неспециалисту и инвестору, где стоит узел GGM-Node, откуда он берёт энергию, чем отличаются M и L и что внутри шкафа. Исполнитель — Claude Code в репозитории сайта (или Claude в артефакте как прототип). Основа — 3D-модуль шкафа ред. 0.3 (`cabinetScene.js`, `cabinetData.js`), он не переписывается, а встраивается как уровень 4.

---

## 1. Роль и режим

Ты — senior 3D/WebGL-разработчик (three.js) и информационный дизайнер технических продуктов. Работаешь до полного выполнения пакета работ, без подтверждений между шагами. Не выдумываешь числа: каждое число берётся из файлов данных (раздел 6) и несёт метку статуса. Где данных нет — `[ДОП]` и пункт в списке открытых вопросов.

## 3. Зафиксированные решения (из уточнений с владельцем 27.10.2026)

1. **Размещение:** узел стоит **внутри здания** в отдельном помещении; на подлёте крыша и стены плавно становятся прозрачными (разрез). Чиллер — снаружи у стены. Контейнер и пристройка не показываются (решение проекта: §35 BauGB, CAPEX).
2. **Варианты объекта:** (a) молочное хозяйство целиком, крупное; (b) молочное хозяйство, среднее; (c) коммерческое или промышленное здание с большой PV на крыше. Переключатель «Объект».
3. **Навигация:** 4 уровня в одной непрерывной сцене: **Объект → Здание → Помещение узла → Шкаф**. Хлебные крошки сверху, «Назад» = обратный пролёт.
4. **Маркеры владельца:** `1 · Здание` (открывает здание и выбор M/L), `2 · Узел GGM` (проводит камеру через помещение в шкаф). Дополнительные информационные метки — буквами (A PV, B накопитель, C ввод/Hausanschluss, D чиллер, E потребители хозяйства), чтобы не путать их с номерами компонентов шкафа 1–32.
5. **Стиль:** тёмный «технический чертёж ночью» по брифу сайта: тёмные матовые поверхности, тонкие светлые рёбра, моноширинные подписи, цвет только у физических потоков.
6. **Данные:** из реестра пилотных хозяйств, **без названий ферм** (бриф сайта §2.2 п. 5).
7. **Для неспециалистов:** автотур «Как это работает», карточка «Что получает хозяйство»; дополнительно — по решению исполнителя (раздел 9).
8. **Результат сейчас:** этот промпт + работающий прототип-артефакт; затем перенос в сайт через Claude Code.

## 4. Архитектура (SOLID, DRY)

```
src/components/cabinet/          ← существующий модуль ред. 0.3, без изменения API
  cabinetScene.js  cabinetData.js  *.d.ts
src/components/site3d/
  siteData.js      ← ВСЕ числа и тексты уровней 1–3: объекты, здания, PV, нагрузки, позиции, тур, карточки
  energyModel.js   ← чистые функции: P_PV(t), P_хоз(t), каскад приоритетов, P_node(M/L), суточные интегралы
  siteScene.js     ← mountSite(host, opts) → SiteHandle: геометрия, потоки, камера, уровни, переходы
  siteScene.d.ts
  SiteViewer.tsx   ← React-обёртка (только в сайте)
scripts/site3d/    ← check-site-data.mjs, render-site.mjs (скриншоты), unit-тесты energyModel
```

- `siteScene.js` создаёт шкаф на уровне 4 через `mountCabinet()` из модуля шкафа (ленивое создание, тот же хост, слой поверх). Геометрия шкафа не дублируется.
- **Бесшовный переход 3 → 4:** помещение узла в сцене объекта строится в той же системе координат, что и комната модуля шкафа (метры; фронт шкафов z = 0, стена здания z = −1,75…−1,95, левая стена x = −3,8). Помещение ставится в здание через одно преобразование `roomToWorld` (поворот + перенос). Камера сцены объекта прилетает в позу `roomToWorld · VIEWS.iso` модуля шкафа, затем за 450 мс проявляется канвас шкафа с `setView('iso', true)`. Поле зрения обеих камер — 34°. Обратный путь симметричен.
- Почему не одна общая сцена: модуль шкафа уже отлажен, имеет свой API, маркеры и тесты. Перенос его геометрии в общую сцену нарушил бы DRY и регрессию ред. 0.3. Компромисс — два WebGL-контекста, из которых активен один.
- `energyModel.js` не зависит от three.js и тестируется отдельно.

### API `SiteHandle`

```ts
  node: number; nodeIT: number; gridImport: number; gridExport: number; heat: number;

  setTime(hour: number, season?: Season): void; play(on: boolean): void;        // анимация суток

  select(markerId: string | null): void;

```

## 5. Уровни, сцены и переходы

| Уровень | Что видно | Камера | Маркеры | Панель справа (телефон — нижний лист) |
|---|---|---|---|---|
| 1 Объект | всё хозяйство или коммерческий участок, поле, дорога, трансформатор, линия сети, солнце | обзор сверху-сбоку, медленное вращение в простое | 1, 2, A–E | паспорт объекта: PV kWp, накопитель, годовое потребление, рекомендуемый класс узла, статусы данных |
| 2 Здание | выбранное здание; соседние здания гаснут до 15 %; потоки энергии крупно | облёт здания | 2, A–E | выбор **M / L**, числа потоков, шкала резерва ввода, что меняется между M и L |
| 3 Помещение | крыша и стены над помещением растворяются; видно помещение узла, ряд шкафов (упрощённый), трассу кабеля к вводу, трубы к чиллеру, огнестойкую дверь | вход сверху в разрез | 2, C, D | требования к помещению (≥ 3,2 × 3,0 м, пол, дверь T30-RS, F30/F90), путь кабеля ≤ 40 м |
| 4 Шкаф | модуль шкафа ред. 0.3 со всеми видами и слоями | поза `iso` модуля | номера компонентов 1–32 | карточка компонента модуля шкафа |

Переходы:
- Пролёт камеры: позиция и цель интерполируются по кривой (cubic in-out), длительность `clamp(0.9 + 0.35·log2(d/10), 0.9, 2.4)` с, где d — путь в метрах; при длинном пролёте камера сначала поднимается (дуга), чтобы не проходить сквозь здания.
- Растворение: крыша здания с узлом (вместе с PV) и стены над помещением — непрозрачность 1 → 0,08 за 600 мс; рёбра остаются видимыми (контур здания читается).
- Смена объекта: затемнение 250 мс → перестройка сцены → проявление 350 мс; уровень сбрасывается на 1.
- Смена M/L: числа потоков пересчитываются; ширина и плотность потоков меняются плавно за 500 мс; в здании пульсирует метка узла; на шкале резерва ввода значение «едет».
- `prefers-reduced-motion`: все пролёты — мгновенно с затемнением 200 мс; частицы потоков — статичные стрелки.

## 6. Данные (`siteData.js`, одна точка правды)

### 6.1 Объекты (из реестра пилотов, анонимизировано)

| id | Название на сайте | PV | Накопитель | Потребление хозяйства | Рекомендуемый узел | Резерв ввода | Источник |
|---|---|---|---|---|---|---|---|
| `dairy-large` | Молочное хозяйство, крупное | 386 kWp [ПОДТВ] | 137 kWh [ПОДТВ], мощность [ОТКР] | 300 MWh/год [МОД] | L | [ОТКР] → в модели 30 kW [ДОП] | реестр пилотов, объект 1 |
| `dairy-medium` | Молочное хозяйство, ≈ 80 коров | 100 kWp [ПОДТВ] | 67 kWh / 60 kW [ПОДТВ] | ≈ 40 MWh/год [ПОДТВ] | M | [ОТКР] → в модели 20 kW [ДОП] | реестр пилотов, объект 2 |
| `commercial` | Коммерческое / промышленное здание | 500 kWp [ДОП] | нет [ДОП] | 600 MWh/год [ДОП] | L | 40 kW [ДОП] | типовой пример, без реального объекта |

Узел: M — 10 kW IT, P_node лето/зима ≈ 14,5 / 11,5 kW, резерв ≥ 16 kW; L — 15 kW IT, ≈ 21,7 / 17,1 kW, резерв ≥ 24 kW [ОЦ] (из `cabinetData.configs` — не дублировать, импортировать).

### 6.2 Модель энергии (`energyModel.js`, метка [МОД], «ясный день, схема»)

- PV: `P_PV(h) = kWp · k_peak(season) · max(0, sin(π·(h − h_rise)/(h_set − h_rise)))^1,3`; лето 5–21 ч, k 0,72; равноденствие 7–19 ч, k 0,60; зима 8–16 ч, k 0,30.
- Хозяйство: база = годовое потребление / 8 760 ч, плюс пики дойки около 6:00 и 17:30 (гауссианы, по 35 % базы), плюс дневная вентиляция летом; среднесуточное значение равно базе.
- Каскад приоритетов (бриф сайта §5.2): PV → 1 хозяйство → 2 накопитель (по правилам хозяйства: заряжается излишком до своей мощности, ночью отдаёт хозяйству) → 3 узел GGM, гибкая часть → 4 экспорт в сеть. Узел: базовая часть 50 % IT круглосуточно [ДОП] + гибкая часть до 100 % IT, когда есть излишек; P_node = P_IT · PUE(season, hour) (PUE 1,45 летом днём, 1,14 зимой [ОЦ]). Недостаток — импорт из сети.
- Тепло: `Q = P_IT + вентиляторы LCP` → отводится чиллером; опция: передача тепловому насосу хозяйства (показывается пунктиром, «опция»).
- Суточные интегралы: доля PV в энергии узла за день, энергия узла, экспорт; показываются в панели с меткой [МОД].
- Unit-тесты: энергобаланс в каждый момент `PV + импорт + разряд = хозяйство + заряд + узел + экспорт` (погрешность < 1e-6); узел не превышает P_node класса; резерв M/L.

## 7. Геометрия и визуальный язык

- Масштаб 1 единица = 1 м. Тёмная палитра брифа: фон `#070908`, поверхности `#121613…#1B211D`, рёбра `rgba(236,240,234,.22)`, подписи `#9AA39C`. Цвета потоков (одинаковые во всей сцене и в шкафу): солнце/PV `#E3A83B`, сеть `#C9CEC8`, узел/данные `#5BC488`, холод `#5B9BE6`, тепло `#EF6656`, накопитель `#B48CE0` [ДОП, согласовать].
- Здания — упрощённые, но узнаваемые: молочный коровник (длинный корпус, двускатная крыша, ветрозащитные сетки, кормовой проход, стойла линиями), машинный зал, жилой дом, силосные башни, круглый навозохранилище, траншейный силос, трансформаторная подстанция, линия сети, поля с полосами, деревья-конусы. Коммерческий вариант: большой зал с плоской крышей и рядами PV восток–запад, офисный блок, рампы, парковка.
- PV — `InstancedMesh` модулей 1,1 × 1,75 м с рамкой, площадь ≈ 5 м²/kWp (схематично); при выработке модули слегка светятся.
- Солнце — направленный свет по дуге времени суток и сезона, видимый диск; ночью сцена темнеет, PV не светится.
- Энергопотоки — частицы по сглаженным трассам (PV → щит здания → хозяйство / накопитель / узел; щит ↔ трансформатор ↔ сеть; узел → чиллер → тепло). Плотность и скорость ∝ kW; подписи kW у трасс (HTML, моноширинный шрифт).
- Помещение узла: огнестойкие стены (светлее остальных), дверь T30-RS, ряд E-шкаф / IT-шкаф / LCP в масштабе 1:1, гидромодуль, кабельный лоток к вводу, трубы через стену к чиллеру, разметка зоны обслуживания на полу.
- Производительность: рендер по требованию + анимационный цикл только когда видны потоки; пауза вне экрана; `pixelRatio ≤ 2`; ≤ 150 k треугольников на объект; бюджет кадра 16 мс на ноутбуке среднего класса, 33 мс на телефоне.

## 9. Контент для неспециалистов

1. **Автотур «Как это работает»** (6 шагов, 5–7 с каждый, пауза/вперёд/назад/выход): (1) объект и солнце; (2) хозяйство потребляет первым; (3) излишек идёт в накопитель и в узел — гибкая часть вычислений днём; (4) ночью узел работает от сети в базовом режиме; (5) помещение узла: закрытый шкаф, холод снаружи, пожарная безопасность; (6) шкаф: компоненты, M и L.
2. **Карточка «Что получает хозяйство»:** фиксированная ежемесячная выплата (без суммы — бриф §2.2 п. 4); никакого нового строительства; планирование, монтаж, эксплуатация, обслуживание — GGM; опция: тепло для теплового насоса. «Что нужно от хозяйства»: помещение ≥ 3,2 × 3,0 м, резерв ввода ≥ 16 / 24 kW, место для чиллера, кабель ≤ 40 м, нет сена и топлива рядом.
3. **Ползунок времени суток и сезона** (решение исполнителя): главный объяснительный инструмент — видно, как гибкая часть узла следует за солнцем.
4. **Шкала резерва ввода** на здании: требуемый резерв M/L против модельного резерва объекта; красный, если не хватает (пример: L на среднем хозяйстве).
5. **Фаза 2 (не в прототипе):** сценарии «запрос сети → 0 kW за ≤ 60 с» [ЦЕЛЬ], «пропадание сети → ИБП и буфер холода ≈ 4 мин», «опция тепла».

## 12. Критерии приёмки

1. Все 4 уровня × 3 объекта × M/L открываются кликом по маркерам и по крошкам; «Назад» возвращает с обратным пролётом; во время пролёта ввод не ломает состояние (очередь или отмена).
2. Переход 3 → 4 без видимого скачка: скриншоты последнего кадра сцены объекта и первого кадра шкафа совпадают по положению ряда (±2 % ширины кадра).
3. Энергобаланс выполняется в каждый час (тест); переключение M/L меняет kW узла, шкалу резерва и тепло; переключение времени перемещает солнце и потоки.
4. Тур проходит все шаги и останавливается по Esc.
5. Скриншоты (светлая тема не нужна): 3 объекта × 4 уровня, телефон 390 × 844, ноутбук 1440 × 900; нет ошибок консоли; нет внешних запросов.
6. Производительность: ≥ 50 fps на уровне 1 на ноутбуке, без утечек после 20 переключений объекта (`renderer.info.memory` стабильно).
